7-day vs 28-day post window — which one do we report?

Movies v12 vs Series v11 · identical event window: Aug 8–14 2026, US, organic discovery · matched-pair delta build · both windows from one scan over one pair set (phase3_window_comparison_*) · min 100 matched pairs per title×segment

Verdict — use 7d for both movies and series. Not a mix. 28d roughly doubles the point estimate but widens the confidence interval 3.19–3.14×, so it is strictly less precise in both universes: median |t| falls 3.45 → 2.03 for movies and 1.03 → 1.01 for series. Report 28d only as a secondary durability ratio — never as a level, and never to rank titles.

Two premises in the question invert on inspection. Series is not consistently higher — movies gain more from the longer window (2.06× vs 1.88×). And movies is not the noisy one; series is — series has 23% sign-flips vs movies' 12%, and a relative CI 3.35× wider — mostly because series carries 288 matched pairs per cell against movies' 889.

0 · Data quality — read this before the numbers

Resolved: 14 series titles had leaked into the movie universe

While validating this comparison, 14 title_ids were found in both exported universes, each contributing an independent estimate to both portfolios at once.

Adjudicated and fixed. A fresh query on 2026-09-28 returned content_type = 'series' for all 14 in dsa.dsac_program_info, with episode-length durations (20.7–87.7 min). Series is correct and keeps them; the movie universe was the leak. The 14 are now excluded from v12_28d_results_data.js — from ALL, WINCMP and WINCMP_IVT alike — and the cross-universe title_id intersection is now zero, asserted in the build.

Root cause. v12_screen_and_7d.sql screens sessions on vs.content_type = 'MOVIE' — that is video_session, i.e. session-level. These 14 programs carry a small MOVIE-labelled sliver alongside their SERIES sessions: 261,730 of 19,802,061 US TVT hrs (1.3%) over Aug 8–14, per title 0.4% (Looney Tunes) to 10.3% (The Temptations). A session-level screen will always admit them. The durable fix is a program-level join (LOWER(i.content_type) = 'movie' against dsa.dsac_program_info) in the upstream SQL; the exclusion list is the export-layer backstop.

It was a regression, not a new bug. build_results_data_v10e_a14.py:10-17 already carried the byte-identical 14-ID set, and v10e_a14_results_data.js contains none of them. v12 reuses the same universe table (top2000_titles_v10e) and dropped the constant when it was cloned, so it re-leaked the identical set.

Every 28d level and every ratio above is therefore an upper bound. Flagged, not corrected — per your call. It does not touch §2: the point estimate and the CI are scaled by the same positive constant viewers × w, so it cancels exactly in |t|.

7 · Recommendation

Ship 7d for both content types. The precision argument points the same direction in movies and series, so there is no case for a mix. Splitting the window by content type would also make cross-type comparison incoherent — a movie's Incr TVT and a series' Incr TVT would be measured over different horizons.

UniverseWindow to shipWhyWhat to change instead of the window
Movies (v12)7d Well powered as-is — 73% of titles significant at 7d, falling to 53% at 28d. Median |t| 3.45 → 2.03. Nothing structural. Report 28d as a durability ratio only.
Series (v11)7d Underpowered at either window (24% → 20%), and 28d makes it worse, not better. A longer window adds variance, not pairs. More matched pairs, or a higher MIN_PAIRS — median 288 pairs/cell vs movies' 889. §4 shows the noise gap largely closes at matched n.
28dsecondary only Use as a content-type-level durability multiplier (movies ≈ 2.06×, series ≈ 1.88×) plus the per-title ratio as a diagnostic. Do not rank titles on 28d and do not quote 28d levels without the upper-bound caveat.

Verification

  • Series cross-build reconciliation (genuine). The series 7d portfolio computed here from v11_28d's WINCMP matches the independently built v11_results_data.js 7d-only dashboard to 0.00% (3,260,015 vs 3,260,015 hrs). Same build family, different table — a real check.
  • Movies has no independent reconciliation target — stated rather than faked. There is no v12 7d-only build on disk, and compare_movies_series_7d_28d.py's movies_7d run reads v10e_a14_results_data.js — a different build with a different contamination screen, so a mismatch there would prove nothing about v12. The obvious substitute is also a tautology: ALL[10] equals WINCMP.d28 to a max relative difference of 0.00e+00 on every cell in both universes. That is kept as an extract-integrity assertion — it proves the two warehouse tables agree, not that the compute is right — and is labelled as such.
  • Structural assertions (replacing the earlier "per-segment sums equal the portfolio total" guard, which was near-tautological — the total is built from those same contributions, so it could never catch a double-count): no duplicate (title_id, seg_idx) keys; zero title_id intersection between the two universes — the assertion that would have caught all 14 leaked titles, now passing at 0 and kept so any future re-leak fails loudly; and fallback_fires == 0 on the pooled SEG_WEIGHT path.
  • Pooled SEG_WEIGHT is dead code today, and the pointers are now correct. TSWEIGHT covers 100% of qualifying cells in both universes at MIN_PAIRS 100 and 300, so the fallback never fires.
